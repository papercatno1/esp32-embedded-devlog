## 回合 #1 TF 卡复查：能写，但不能跟 LCD 一起挂着

**起因**：用户把 TF 卡格式化后插入，要确认卡行不行。

**过程**
1. 板子在线（`ver 0.3.4`、`up 14451`、`notes 3`、`ifs ffat`）。运行时 `M` → `OK M SDHC 29818 w=1`，说明**格式化后卡确实可写了**。
2. 顺手把「开机挂卡」加进固件（在 `ui_begin()` 之前探卡 + 3 次重试），并加了 FFat→SD 一次性迁移。
   结果开机后 `M` → `OK M ? 29818 w=0`：`cardType()` 返回 `CARD_NONE`，卡**掉线**了。
3. 试着把探卡挪到 LCD 初始化之后（并 `ui_bus_recover()`），仍然是 `w=0`。
4. 结论：`SCK 39 / MOSI 38` 被 LCD 与卡共用，**卡长期挂着就会被 LCD 的 SPI 重配弄掉**。
   运行时一次性挂载（挂 → 用 → 卸）才是稳的。

**改法（固件 0.3.5）**
- 开机不挂卡，彻底避免抢总线
- `M` 指令：`SD.end()` → 重新 `sd_probe()` → 测类型/容量/写测试 → `SD.end()` → `notes_refresh_img_fs()` 重新判定 → `ui_bus_recover()`
- 图片继续存内部 FFat（10 MB，3 张 320×212，重启不丢）

**验证**
- `OK M SDHC 29818 w=1`（临时挂载可读写）
- 硬复位后 `notes:3 / isz:17 / ifs:"ffat"`，`P 3` 显示图片 `bk=18478` → 图片仍在、正常绘制

**踩坑**
- `notes.cpp` 里 `notes_refresh_img_fs()` 用到了下面才定义的 `img_path()` → 需要前置声明，否则 `error: 'img_path' was not declared in this scope`
- `notes_refresh_img_fs()` 在 `notes_begin()` 之前调用时 FFat 还没挂载，迁移会静默不执行 → 必须放到 `notes_begin()` 里 FFat 挂好之后
- 开机写测试连续失败，但卸掉再挂就成功：说明不是卡的问题，是"常驻挂载 + 共用总线"的组合问题

## 今天的成果
- TF 卡确认可用（`SDHC 29818 MB`，可读可写），改为按需挂载
- 图片存放策略定稿：内部 FFat 持久化，卡留给后续大容量场景

## 回合 #2 纠正：卡和屏幕本来就能共存（上一回合结论是错的）

用户指出：工厂 demo 就是 LVGL 界面 + 摄像头 + SD + WiFi 同时跑，卡和屏不可能不能共存。核对后确认用户是对的。

**真正原因**
上一版我在挂卡之后调了 `ui_bus_recover()`（内部 `s_bus->begin(); s_gfx->begin()`），
这次"重建 LCD 总线"会把卡那一次的 SPI 会话弄死 —— 于是 `cardType()` 变 `CARD_NONE`、写测试 `w=0`。
把卡当成"不能共存"，实际是我自己的代码把卡踹下了总线。

**改法**
1. SD 用 **FSPI**（与 LCD 同一个 SPI 外设），不再用 HSPI 另起外设抢同一组引脚（`SCK 39 / MOSI 38 / MISO 40 / CS 41`）
2. 挂卡放在 LCD 初始化**之后**，挂完**不再重建 LCD 总线**
3. `M` 指令保留：报告类型/容量/可写性（`OK M SDHC 29818 w=1`）

**验证（关键三连）**
- `M` → `OK M SDHC 29818 w=1`
- `P 2`（LCD 完整重画一页）→ `OK P 2`
- 再 `M` → 仍然 `w=1` → **LCD 画图与卡读写互不影响**
- 图片改存卡：`ifs:"sd"`、卡上索引 `isz:18`
- 硬复位 → `notes:3`、`ifs:"sd"`、`P 3` 图片正常显示（`bk=18478`）

**教训**
- 把自己代码引入的副作用（重建总线）当成"硬件限制"，是这次误判的根源
- 共用 SPI 的外设，关键不是"能不能共用引脚"，而是"谁在什么时候重配总线"

## 回合 #3 · 三模式骨架与 App 功能菜单

**需求（用户）**
App 作为主入口，启动看到功能菜单：① 原生系统（设备进入初始界面，手机端也有对应界面）② 照相系统（第一天的 webcam，改到安卓端）③ 票据屏；以后新功能往菜单里加。

**先说清三条硬约束**
- ESP32 只有 `app0 / app1` 两个固件槽，同一时刻只能跑一个 → 只能做"一个固件 + 三个模式"，不能做"三个系统"
- 原生系统选**复刻**（在我们固件里做系统信息页），不选"把出厂 bin 放 app1 切过去"：切过去 BLE/WiFi 都不在，手机彻底失去控制，而这屏没有触摸
- 照相必须走 WiFi（BLE 传不动 MJPEG 帧），App 端先用 WebView 起步

**分区扩容**
原来 app 槽各 3 MB，票据屏已占 1.97 MB，合并照相（0.94 MB）会顶到天花板 → 改成各 4 MB，ffat 收到 7.875 MB：

```
app0,   app, ota_0, 0x10000,  0x400000,
app1,   app, ota_1, 0x410000, 0x400000,
ffat,   data, fat,  0x810000, 0x7e0000,
```

刷写必须先清 otadata（`erase-region 0xe000 0x2000`），否则会启动到另一个槽的旧固件。改完实测图片仍在卡上（`notes:1 ifs:"sd" isz:18 bk:18478`）。

**固件 0.4.0**
- `MODE sys|note|cam` 模式状态机；`SYS` 一次取全系统信息；`/status.json` 加 `mode`
- 系统信息页：芯片 / PSRAM / FLASH / TF 卡 / 电池 / 芯片温度 / 可用内存 / 已运行 / WiFi / 蓝牙，3 秒自刷新，页脚显示版本
- 排版踩坑：10 行按 19px 行距会压到页脚线（212）以下 → 改 `y0=38, lh=17`

**App 0.6.0「ESP32 控制台」**
- 启动页改成菜单（原生系统 / 照相占位 / 票据屏）
- 原生系统页：扫描连接 → 发 `SYS` → 把 `k=v` 转中文列表 → 「切到系统页」发 `MODE sys`
- APK 命名改为 `ESP32控制台-<版本>-debug.apk`（脚本从 `versionName` 取版本号）

**踩坑**
1. Python 生成 Kotlin 源码时，非 raw 字符串里的 `\n` 被吃成真换行 → `Expecting ','`；Kotlin 里必须写成 `"\n"`
2. `versionCode = 9` 是 `=` 赋值风格，字符串替换 `versionCode 9` 不匹配 → 版本号没更新，APK 名字还是 0.5.0
3. 构建脚本要用 pwsh 调 `& scripts\build_apk.ps1`；用 `powershell -File` 会按 ANSI 读 UTF-8 中文注释，报 `Unexpected token 'JDK'`

**待校准**：`SYS` 里 `bat=2.73V`，出厂界面显示 3.87V —— 分压系数要按原理图核对。

**验证**
- `MODE sys` → `/status.json` `mode:1`、回执 `OK MODE sys`
- `SYS` → `OK SYS ver=0.4.0 mode=sys psram=7MB flash=16MB tf=29818MB bat=2.73V temp=37C heap=180KB wifi=1 ble=1 up=43s notes=1`
- APK 构建成功：`dist\ESP32控制台-0.6.0-debug.apk`（2136.6 KB，versionCode 9）
